# Forecast the next hop, then prove it honestly

Lateralis can become a credible self-hosted B2B platform at zero cost. Its defensible core is not the GAT+GRU architecture, which Euler, Argus, Jbeil and Akamai Hunt already resemble. The core is three things no competitor publishes together: **calibrated next-hop forecasts evaluated with ranking metrics on real data**, forecast-weighted choke-point defenses, and LLM agents grounded in those forecasts that never send raw identities off the machine. The real-data foundation should be **LANL 2015 auth.txt + redteam.txt**. It is the only public dataset that is real, carries user→computer authentication, and already matches the project's `(time, user, src, dst)` schema. DARPA OpTC serves as a cross-environment check, and an emulated Samba/Zeek Docker lab supplies the multi-campaign ground truth that LANL's single intrusion cannot. The evaluation story matters more than any architecture choice. A July 2026 independent re-evaluation found that headline lateral-movement results of 99% AUC drop to **0.02–0.09% average precision on LANL** and to **near-random AUC (43–53%) on OpTC lateral-movement events** under realistic preprocessing. If Lateralis adopts that protocol from day one, adds TGB-style next-hop ranking with an EdgeBank baseline, and reports calibration, its numbers will be modest but defensible, and almost no one in the field can say the same. On the platform side, everything fits a Docker Compose bundle with profiles on a 16 GB laptop: a core of about 2–3 GB plus a 4–6 GB lab. The four agents run on LangGraph with mandatory human-approval interrupts, routed through LiteLLM across Groq and other no-card free tiers for roughly 2,000 LLM calls a day, behind a Presidio pseudonymization gateway. Free-tier terms, Samba telemetry realism and several licences remain unverified. Check them before you build on them.

## LANL 2015 is the only real dataset that fits next-hop forecasting

Lateralis has a narrow data requirement: real enterprise authentication with distinct users and computers, plus labelled multi-hop intrusions whose hop order can be rebuilt. Only one public dataset meets all of it. **LANL 2015 "Comprehensive, Multi-Source Cyber-Security Events"** covers 58 consecutive days of de-identified events from LANL's corporate network: **1.65 billion events, 12,425 users and 17,684 computers**, about 12 GB compressed. Of that, auth.txt.gz is 7.2 GB, and redteam.txt.gz is just 4.8 KB ([LANL cyber1](https://csr.lanl.gov/data/cyber1/)). Every auth row carries source and destination user@domain, source and destination computer, authentication type, logon type, orientation and success/failure. redteam.txt lists `time, user@domain, src, dst` tuples for known compromise events. Access is a free e-mail form under CC0 1.0 ([LANL cyber1](https://csr.lanl.gov/data/cyber1/)). The schema is a strict superset of Lateralis's current synthetic format, so only the loader changes.

The catch is how thin LANL's ground truth is. **Only 0.0000713% of roughly 1.05 billion auth events are malicious** ([Kushwaha et al., arXiv 2208.13524](https://arxiv.org/pdf/2208.13524)). All labelled events belong to **one simulated intrusion, almost all from source host C17693**, and the red team stops on day 30 ([Larroche 2026, arXiv 2607.29390](https://arxiv.org/pdf/2607.29390)). Under Larroche's recommended preprocessing (all remote LogOn events, testing on everything after the first 41 hours), the evaluation set is **16,159 nodes, 369,569,626 events and 702 malicious events** ([Larroche 2026](https://arxiv.org/pdf/2607.29390)). Two consequences follow. First, LANL red-team labels must never be used for supervised training: Larroche says the dataset "should thus only be used to evaluate unsupervised learning methods" ([Larroche 2026](https://arxiv.org/pdf/2607.29390)). Second, LANL alone gives too few independent next hops to forecast with statistical power. Lateralis needs a second source of multi-campaign ground truth. The lab described below is the zero-cost answer.

**DARPA OpTC** is the right secondary, cross-environment dataset, with caveats. It holds about 1 TB of compressed eCAR JSON from 500 of 1,000 synthetic hosts, released for public distribution ([FiveDirections/OpTC-data](https://github.com/FiveDirections/OpTC-data)). It has **no event-level labels**, only a red-team report. How you derive labels changes the malicious count enormously: host-based labelling gives about 25,000 flows, process-based labelling gives 563, and Larroche's hybrid gives 1,359, of which 249 relate to lateral movement ([Larroche 2026](https://arxiv.org/pdf/2607.29390)). Larroche publishes preprocessing and label code at `cl-anssi/LMDEval`. After deduplication it yields **897 nodes, 36.2 million events and 244 lateral-movement events** ([Larroche 2026](https://arxiv.org/pdf/2607.29390)). OpTC is machine-only, so the user layer of Lateralis's heterogeneous graph drops out there.

**LMDG (2025)** is the only public dataset with labelled multi-hop Active Directory attacks: 35 attacks of **up to 7 hops** (Pass-the-Hash, Pass-the-Ticket, Golden/Silver Ticket, delegation abuse and others) across 25 VMs. It is also enormous, at 253 GB compressed without router data and 944 GB uncompressed, and it states no licence ([LMDG, arXiv 2508.02942](https://arxiv.org/html/2508.02942v1)). It suits path-ranking evaluation only if disk allows. Flow datasets (CICIDS2017, CSE-CIC-IDS2018, UNSW-NB15, the NetFlow v2/v3 family) are free, but they are machine-only, dominated by DoS and scanning, and carry documented label errors ([KU Leuven, Engelen et al.](https://lirias.kuleuven.be/retrieve/713070)). Some have absurd attack ratios, such as NF-BoT-IoT-v3 at 99.7% attacks ([UQ NIDS datasets](https://staff.itee.uq.edu.au/marius/NIDS_datasets/)). LANL 2017 has no labels at all ([LANL 2017](https://csr.lanl.gov/data/2017/)). DARPA TC and ATLASv2 are single-host provenance data, not enterprise authentication graphs.

| Dataset | Role for Lateralis | Real? | User→computer | LM labels | Laptop practicality |
|---|---|---|---|---|---|
| LANL 2015 | **Primary** | Real enterprise | Yes | 702 events, one intrusion | Stream 7.2 GB gz; aggregate per snapshot |
| DARPA OpTC | **Secondary** (cross-environment) | Synthetic testbed | No | Derived; 244 LM via LMDEval | Pull FLOW-START subset only; never the full 1 TB |
| Docker lab (own) | **Multi-campaign ground truth** | Real telemetry, emulated attacks | Yes (Samba/Zeek) | By construction | Generated locally |
| LMDG | Optional path-ranking check | Synthetic AD | Partly | 35 attacks, up to 7 hops | 253 GB+; only if disk allows |
| CSE-CIC-IDS2018 / NF-v3 | Optional flow robustness check | Synthetic | No | Per-flow, noisy | Free S3, no credentials needed |

### Process LANL by streaming, filtering and aggregating, never by loading

Published systems ran on far bigger machines. Euler ran on **512 GB of RAM** and split the 69 GB raw auth.txt into 10,000-second chunks ([Euler, ACM TOPS 2023](https://isaiahjking.com/papers/EulerACM.pdf)). On 16 GB, the pipeline has to stream. Read `auth.txt.gz` with polars `scan_csv` or pandas chunks. Keep remote LogOn events (src ≠ dst) with outcome retained. Write day-partitioned Parquet. Then aggregate to `(snapshot, user, src, dst, count)` at 1 hour, Lateralis's current setting, and optionally at 30 minutes to match Euler's δ = 1800 s ([Euler TOPS 2023](https://isaiahjking.com/papers/EulerACM.pdf)). Expect up to roughly 370 million filtered rows before aggregation, bounded by Larroche's figure. Do not apply the popular shortcuts. **NTLM-only filtering inflates metrics because LANL's attacks happen to use NTLM**, downsampling benign users fakes a low false-positive rate, and dropping local or computer accounts discards some malicious events ([Larroche 2026](https://arxiv.org/pdf/2607.29390)). Use a "dev subset" of days 1–30, which contains every red-team event, for fast iteration. Report final numbers on the full Larroche protocol, and add a clearly labelled "14-day NTLM" variant only for comparison with Euler, Argus and CyberGFM numbers. Do the one-time filtering on free Colab disk if laptop disk runs short. Colab's T4, roughly 12 GB RAM and roughly 100 GB disk were taken from your brief and were not re-verified. For OpTC, stream-parse only `object==FLOW && action==START` from the evaluation-day files, or reuse LMDEval's output. Merge each host's six IP addresses into one node, as Larroche does ([Larroche 2026](https://arxiv.org/pdf/2607.29390)).

## Published 99% AUCs collapse to near-zero precision under fair evaluation

The lateral-movement graph literature almost entirely frames the problem as **unsupervised edge anomaly detection** on LANL and OpTC. **Euler** (NDSS 2022, extended in ACM TOPS 2023) stacks a GNN on an RNN over snapshots. **Argus** (IEEE S&P 2024, MIT-licensed) uses an MPNN-GRU and optimises AP directly. **Jbeil** (S&P 2024) does inductive TGN-style link prediction and reports about 99% AUC. **PIKACHU** uses temporal-walk embeddings. **CyberGFM** (Jan 2026) does BERT-style pretraining over random walks and reports LANL AUC/AP of 0.9994/0.76 ([CyberGFM, arXiv 2601.05988](https://arxiv.org/html/2601.05988); [Argus](https://github.com/C0ldstudy/Argus); [Jbeil, NSF PAR](https://par.nsf.gov/servlets/purl/10540681)). Lateralis's GAT encoder, GRU memory and MLP link decoder on hourly snapshots belong to the same family as Euler and Argus, so those two are its natural same-family baselines.

Larroche's ANUBIS '26 re-evaluation recomputed PIKACHU, Euler and Argus under one realistic policy, with event-level metrics on identical test events. The numbers fell hard:

| Method | LANL AUC reported → fair | LANL AP (%) reported → fair | OpTC LM-only AUC reported → fair |
|---|---|---|---|
| PIKACHU | 94 → 78.28 | n/a → 0.00 | 99 → 50.74 |
| Euler (GCN-GRU) | 99.12 → 97.97 | 5.23 → **0.02** | 88.8 → 52.90 |
| Argus (MPNN-GRU) | 99.83 → 98.44 | 32.27 → **0.09** | 99.7 → 43.23 |

Source: [Larroche 2026, Tables 5–6](https://arxiv.org/html/2607.29390v1). On LANL the ranking survives (Argus > Euler > PIKACHU). On OpTC, Argus loses its lead, and Larroche concludes that "lateral movement detection remains an open problem." The supervised results that look best (LMDetect at 99.99 AUC, Jbeil at 99.73) come from random or node-subset splits of that single LANL intrusion ([LMDetect, arXiv 2411.10279](https://arxiv.org/html/2411.10279)). CyberGFM explicitly used a random 80/10/10 split, not a temporal one ([CyberGFM](https://arxiv.org/html/2601.05988)). Treat none of these as targets. Provenance IDSs such as Kairos, Orthrus, MAGIC, Flash and Velox detect at host level on system-call graphs, and PIDSMaker recommends **≥100 GB RAM** to run them ([PIDSMaker, arXiv 2601.22983](https://arxiv.org/html/2601.22983v2)). Cite them as related work; do not run them as baselines.

Three independent critiques explain the inflation. Larroche covers inconsistent splits, filters and labels. Bilot et al., PIDSMaker and Moon et al. cover data snooping, checkpoint selection on test labels, neighbourhood credit and single-run reporting. Moon et al. found that **only 7 of ThreaTrace's 994 alarms carry its own attack label**, and that removing test-label checkpoint selection cuts precision by 0.16–0.33 ([Moon et al., arXiv 2609.33532](https://arxiv.org/abs/2609.33532)). The third critique comes from temporal link-prediction benchmarking. There, a pure-memorisation **EdgeBank** baseline does surprisingly well because edges recur, and rankings change once you use historical rather than random negatives ([Poursafaei et al., NeurIPS 2022](https://arxiv.org/abs/2207.10128v2)). Authentication graphs are highly repetitive, so EdgeBank is a mandatory baseline for Lateralis.

### Next-hop forecasting is a genuine, defensible novelty

Almost every graph lateral-movement paper scores edges that have already happened. True **next-hop forecasting** on real enterprise graphs is rare. The nearest precedents are Tiresias, which predicts the next security event per machine with RNNs at precision up to 0.93 ([Tiresias, CCS 2018](https://ar5iv.labs.arxiv.org/html/1905.10328)); Danneman & Hyde's next-compromised-host ranking, trained on simulation, with no published metric values ([arXiv 2104.13195](https://arxiv.org/abs/2104.13195)); and knowledge-graph attack-path prediction scored with MRR and Hits@N ([MDPI Electronics 2026](https://www.mdpi.com/2079-9292/15/3/552)). No peer-reviewed next-hop benchmark on LANL or OpTC was found. That gap is Lateralis's research claim, provided it is scored the way temporal-graph ML scores link ranking: **MRR against many negatives, including historical ones, as in TGB** ([TGB](https://ar5iv.labs.arxiv.org/html/2307.01026)). TGB 2.0 shows that 1-vs-all evaluation gives the lowest, most honest MRR ([arXiv 2406.09639](https://arxiv.org/pdf/2406.09639)).

Calibration is the second novelty, and it matters for Lateralis specifically. Yen's algorithm runs on edge costs of −log p, so a path's rank depends on probabilities being calibrated across edges, and miscalibration compounds along a path. ECE, Brier score and NLL have precedent in malware and flow-IDS work ([Li et al., ACSAC 2021](https://arxiv.org/pdf/2109.09654)), but **no graph lateral-movement or provenance-IDS paper found reports calibration**. Calibration also degrades under novel attacks, and recalibrating on a small shifted sample fixes it ([IJACSA 2025](https://thesai.org/Downloads/Volume17No8/Paper_12-When_Calibrated_Detectors_Meet_New_Attacks.pdf)). That argues for evaluating on a later period and on a second dataset.

### The protocol to adopt

| Element | Specification |
|---|---|
| LANL split | Larroche policy: all remote LogOn, keep machine and built-in accounts, no downsampling; train ≤ 41 h; test on the rest, including benign days 31–58 ([Larroche 2026](https://arxiv.org/html/2607.29390v1)) |
| Validation | Carve from inside the training window (Euler holds out the last 5% of training snapshots plus 5% masked edges ([Euler TOPS 2023](https://isaiahjking.com/papers/EulerACM.pdf))). Never tune on red-team events. The notes' suggestion of "days 3–7" would overlap the red-team period, so do not use it |
| OpTC split | Internal FLOW-START only, deduplicated, IPs merged per host; train 17–22 Sep, test 23–25 Sep; report LM-only and all-malicious separately ([Larroche 2026](https://arxiv.org/html/2607.29390v1)) |
| Task A: detection | Event-level AUC, **AP as the primary metric**, FPR at TPR 0.9/0.99, precision@k, alerts/day at the operating point (Hopper reported 94.5% of attacks caught at under 9 FPs/day ([Hopper](https://arxiv.org/pdf/2105.13442))) |
| Task B: forecasting | For each red-team edge u→v at t, rank candidate destinations; Hits@1/5/10 and filtered MRR (1-vs-all, plus historical + random negatives); top-k path hit rate from Yen's (k = 1, 5, 10); lead time in snapshots; bootstrap 95% CIs over red-team events |
| Calibration | ECE (15 equal-mass bins), Brier, NLL, reliability diagrams, before and after temperature scaling fitted on validation; also on a later or shifted period |
| Baselines | Random, EdgeBank (∞ and time-window), recency/frequency, degree, historical-destination; Euler and Argus (BCE loss); TGN, TGAT, GraphMixer and DyGFormer via DyGLib (MIT) ([DyGLib](https://arxiv.org/abs/2303.13047v3)); static GAT. All tuned on the same budget |
| Ablations | No GRU, homogeneous graph, no edge features, snapshot 15 min / 1 h / 6 h (event-level metrics), no temperature scaling, decoder type, negative-sampling strategy, Yen's k and cost function, defense recommendations vs random/degree isolation |
| Reporting | ≥5 seeds, mean ± std; wall-clock and peak RAM on stated hardware; a preprocessing/label table per dataset; a comparability note whenever quoting published numbers |

Feasibility on your hardware follows from graph size. Heuristic baselines run in minutes on the laptop. Euler and Argus on the 14-day LANL subset (15.6k nodes, 3M edges) and on OpTC (~900 nodes) are realistic on a Colab T4. Argus's AP loss is memory-heavy, and its README offers `--loss bce` to avoid out-of-memory errors ([Argus](https://github.com/C0ldstudy/Argus)). CyberGFM's LANL pretraining took about 12,000 s on a V100 32 GB ([CyberGFM](https://arxiv.org/html/2601.05988)), and full-LANL end-to-end training is out of scope without aggregation. These tiers are inferences from published hardware; no T4 runtimes were found. One licensing caution: Euler has **no licence**, so run it for comparison but do not redistribute its code ([GitHub API](https://api.github.com/search/repositories?q=repo:iHeartGraph/Euler+repo:C0ldstudy/Argus+repo:cybermonic/CyberGFM)).

## A 4–6 GB Samba-and-Zeek lab fits beside the platform on 16 GB

The stack has one organising principle: **ship adapters, not a SIEM.** Most enterprises already run a collector, so Lateralis should sit downstream of Wazuh, Zeek, Windows Event Forwarding or OpenTelemetry, normalise everything into a slim **OCSF** subset, and keep its own footprint small. OCSF has been a Linux Foundation project since November 2024 ([Linux Foundation](https://www.linuxfoundation.org/press/open-cybersecurity-schema-framework-ocsf-joins-the-linux-foundation-to-optimize-critical-security-data?hsLang=en)), and its **Authentication class (UID 3002)** carries user, auth protocol, logon type and source and destination endpoints ([Tenzir OCSF 1.4.0](https://docs.tenzir.com/reference/ocsf/1-4-0/classes/authentication)). That maps one-to-one onto LANL-style tuples, so the GNN trains on public data and runs on customer data through the same schema.

BloodHound deserves a specific framing. It models **static** privilege reachability: who *can* reach Domain Admin. Lateralis models **observed, time-ordered** behaviour: who *is* moving, and where next. BloodHound edges such as AdminTo, HasSession and MemberOf make strong static edge features for the temporal GNN, and its REST API with HMAC-signed tokens makes them easy to pull ([BloodHound API](https://bloodhound.specterops.io/integrations/bloodhound-api/working-with-api)).

### The attack lab: Samba AD, Zeek and Caldera in pure Docker

Windows-realistic labs don't fit. GOAD on Ludus needs a **dedicated Debian host that "will completely take over the machine"** ([Ludus](https://docs.ludus.cloud/docs/environment-guides/goad)), and DetectionLab has been unmaintained since 2023 ([cybersectools](https://cybersectools.com/tools/detection-lab)). The feasible design is a Linux lab built around a **Samba 4 AD domain controller**. Samba's JSON audit log, enabled with `auth_json_audit:3`, emits authentication events with **Windows-style `eventId` and `logonType` fields**, service descriptions (LDAP, SMB2, NETLOGON), password type, status, remote address and account. Password-change and group-change events carry Windows IDs such as 4723/4724 and 4728–4762 ([Samba wiki: JSON audit](https://wiki.samba.org/index.php/Interpreting_JSON_Audit_Logs)). Only the DC's KDC logs Kerberos authentication; domain members cannot ([Samba wiki: audit logging](https://wiki.samba.org/index.php/Setting_up_Audit_Logging)). **Zeek** on the lab bridge adds network-level `kerberos.log`, `ntlm.log`, `smb_*.log`, `dce_rpc.log` and `ssh.log` without host agents ([Zeek SMB logs](https://docs.zeek.org/en/master/logs/smb.html); [Zeek SSH logs](https://docs.zeek.org/en/lts/logs/ssh.html)). **Caldera**, now Apache-2.0 under the `apache/` GitHub org and runnable from `ghcr.io/apache/caldera`, drives the attacks through its Sandcat agent and Atomic plugin ([apache/caldera](https://github.com/apache/caldera)).

The proposed lab profile has `dc1` (Samba AD DC), two domain-joined Debian workstations with sshd, a Samba file server, a vulnerable web app, a database with reused credentials, an attacker container (impacket, NetExec, Caldera), a Zeek sensor, and Vector writing OCSF Parquet. The attack chain runs from a password spray, to SSH with valid accounts (T1078/T1021.004), to Kerberoasting (T1558.003), to SMB to the file server (T1021.002), to DCSync against Samba (T1003.006), to pass-the-hash/ticket (T1550.002/.003). Every step leaves Samba, Zeek and sshd traces, and Caldera operation reports supply ground truth by construction. The estimated total is **4–6 GB, unmeasured**. Caldera's own guidance says 8 GB+ ([apache/caldera](https://github.com/apache/caldera)), which looks generous for a Python aiohttp server, but measure it with `docker stats`. Be honest about realism. Samba does not reproduce 4648, the 4768/4769 split, or 4672. It was not confirmed whether Kerberos TGS requests produce separate events, and one user reported auth logging breaking after a Samba upgrade ([samba mailing list](https://lists.samba.org/archive/samba/2021-November/238734.html)). No source confirmed that RustHound-CE or bloodhound-ce-python work against Samba AD. Present it as a "Linux/Samba AD lab", and keep LANL as the Windows-native evaluation.

### Packaging follows BloodHound CE's pattern

Ship one `docker-compose.yml` with **profiles**. `core` is the default: FastAPI API, GNN worker, Postgres/AGE, a DuckDB volume, Vector and the React UI, about 2–3 GB. Opt-in profiles are `lab` (4–6 GB), `bloodhound` (2–3 GB), `soar` (2–4 GB) and `wazuh` (6–8 GB, mutually exclusive with `lab` on 16 GB). Add health checks with `depends_on: condition: service_healthy`, **bind to 127.0.0.1 by default** as BloodHound CE does ([BloodHound CE quickstart](https://bloodhound.specterops.io/get-started/quickstart/community-edition-quickstart)), and generate secrets in `.env`. RAM figures are estimates. One unverified but critical detail: Docker Desktop on Windows defaults WSL2 to about half of host RAM, roughly 8 GB here, so `core` + `lab` may need a `.wslconfig` change. Keep AGPL/GPL components (Shuffle, Tracecat, Neo4j CE, Wazuh, MISP) as unmodified, separately pulled images, and ship a `THIRD_PARTY_LICENSES` file. That keeps Lateralis's own licence choice unconstrained.

## Four agents can run on roughly 2,000 free LLM calls a day

### LangGraph as orchestrator, with approval enforced in code

**LangGraph (MIT)** is the safest orchestrator. Its `interrupt()` pauses a node, checkpoints state to SQLite or Postgres, and resumes with `Command(resume=...)` carrying approve, edit or reject decisions, including edited tool arguments ([LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)). One subtlety shapes the design: on resume the node **re-runs from its start**, so side effects must sit after the approval point. That is exactly where SOAR execution belongs. **PydanticAI (MIT)** is the lighter alternative, with native `requires_approval`, 30+ providers, AG-UI streaming and MCP client and server support. **Microsoft Agent Framework 1.0** (MIT, GA April 2026) is a third option ([Pydantic comparison, vendor-written](https://pydantic.dev/articles/best-python-ai-agent-frameworks); [Microsoft devblog](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/)). Avoid the OpenAI Agents SDK, whose non-OpenAI providers are "best-effort and beta" and whose tracing uploads to OpenAI by default. Avoid CrewAI for the response agent, because its webhook human-in-the-loop is enterprise-only ([Pydantic](https://pydantic.dev/articles/best-python-ai-agent-frameworks)).

Use a **supervisor with four specialist sub-graphs, not a group chat**. Each agent gets a tool allow-list enforced in code. The analyst/triage agent has read-only tools: graph query, event fetch, ATT&CK lookup, report draft. The response agent can only call `propose_action`; a non-LLM approval service executes after a human clicks Approve. The red-team agent can only call Caldera, network-bound to the lab, and every operation launch needs approval plus a scope check. The copilot is read-only and has no path to the response or red-team agents. Expose these tools through a single **first-party MCP server**. The current MCP spec is the **2026-07-28** revision, stateless, with HTTP+SSE deprecated in favour of Streamable HTTP ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)). Treat community security MCP servers (ATT&CK, Wazuh, Caldera) as untrusted third-party code, because the OWASP MCP Top 10 now lists **tool poisoning (MCP03)** and contextual-payload injection (MCP06) ([OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/)).

**LiteLLM Router (MIT)** handles the cascade with `order` priorities, per-deployment `rpm`/`tpm`/`rpd`/`tpd` limits, retries with exponential back-off on 429s, cooldowns and context-window fallbacks ([LiteLLM routing](https://docs.litellm.ai/docs/routing)). The daily ceiling is roughly 2,000 calls, an estimate, and Groq's **8K tokens/minute** limit is the real bottleneck for agent loops. Gate the LLM behind the GNN, so that only high-score forecasts trigger triage, and summarise tool outputs before they enter the context.

### Pseudonymize with stable typed tokens, not ciphertext

Put a `RedactionGateway` in front of LiteLLM, as a pre/post-call hook or FastAPI middleware. It runs **Microsoft Presidio** with regex-first `PatternRecognizer`s for `C\d+` hosts, `U\d+@DOM\d+` users, IPs, FQDNs, e-mails and SIDs. Presidio's only built-in reversible operator is `encrypt`, which emits ciphertext that means nothing to an LLM ([Presidio encryption tutorial](https://microsoft.github.io/presidio/tutorial/12_encryption)). Its official pseudonymization sample instead defines an `InstanceCounterAnonymizer` that emits per-type indexed tokens such as `<HOST_17>` ([Presidio pseudonymization sample](https://microsoft.github.io/presidio/samples/python/pseudonymization)). Persist the mapping in local SQLite keyed by tenant and incident, because custom-operator state dies with the engine instance. Tools receive tokenized arguments and de-tokenize internally, and tool results are re-tokenized before returning to the model. **Reject any token not in the mapping**, such as a hallucinated `HOST_99`, before it reaches SOAR. Typed, entity-unique placeholders are the right choice, since generic tags like a single `<NAME>` make distinct entities hard to tell apart ([arXiv 2411.05978](https://arxiv.org/html/2411.05978v1)). Retrieval-heavy tasks suffer most under anonymization ([arXiv 2609.11335](https://arxiv.org/pdf/2609.11335)). For security data, IPs and hostnames are the investigation's join keys. Keep coarse attributes in the token (`HOST_17[dc]`, `IP_3[internal]`) and preserve subnet structure. That last point is a hypothesis to test, not a finding. Also expect detection to be imperfect: the best F1 on CyberPII-Bench for sanitizing PII in security data was only **0.46** ([CAIBench](https://arxiv.org/html/2510.24317)). Measure leakage on logged outbound prompts rather than assuming it is zero.

### Treat every log field as attacker-controlled

Command lines, user agents, hostnames and file names are written by the attacker, so the analyst agent is an indirect-prompt-injection target by design. Redaction does not defend against this. The defences have to be architectural. Keep the code-enforced allow-lists above. Wrap untrusted fields as delimited JSON with `untrusted=true`, truncated and stripped of control and zero-width characters. Use a **dual-LLM pattern**, where a tool-less quarantined model (ideally local) turns raw blobs into schema-validated fields before the privileged agent sees them ([Willison on CaMeL](https://simonwillison.net/2025/apr/11/camel/)). CaMeL goes further, compiling requests into a capability-tracked program, and reportedly eliminates nearly all AgentDojo attacks ([arXiv 2505.02077](https://arxiv.org/pdf/2505.02077)). Run a classifier pass with **Llama Prompt Guard 2**, which Groq hosts free at 14.4K requests/day ([Groq](https://console.groq.com/docs/rate-limits)). Validate tool arguments against Pydantic schemas and known tokens, and keep an immutable audit log of every tool call and approval.

### Observability: Phoenix on the laptop, Langfuse later

**Arize Phoenix** runs as a single container, is OpenTelemetry/OpenInference-native, and has instrumentors for LangGraph, PydanticAI and LiteLLM. Its licence is **Elastic License 2.0**, which is source-available, not OSI open source ([Phoenix](https://github.com/Arize-ai/phoenix)). **Langfuse** is MIT outside its `ee` folders, but its documented minimums add up to well over 16 GB: ClickHouse at 8 GiB, plus web, worker and Postgres at 4 GiB each, plus Redis ([Langfuse ClickHouse guide](https://langfuse.com/resources/engineering/clickhouse-for-self-hosted-langfuse)). Instrument with OTel so you can switch later; the GenAI semantic conventions are still in Development status ([OTel GenAI spans](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-spans/)). Capture traces **after** redaction, and keep them local.

## Each agent needs a lab-grounded benchmark, not just public quiz sets

Public security benchmarks mostly test knowledge, not agency. A recurring finding is that models score **70–89% on knowledge but about 20–50% on execution** ([CAIBench](https://arxiv.org/html/2510.24317)). The few agentic benchmarks show modest absolute numbers. On **ExCyTIn-Bench**, Microsoft's multi-hop SQL investigation over Sentinel-style logs, base-agent rewards span 0.085 (Phi-4) to 0.368 (o4-mini), with Qwen-3-32B at 0.182 and Llama-4-Maverick at 0.290 ([arXiv 2507.14201](https://arxiv.org/html/2507.14201v1)). **AutoPenBench** shows 21% success autonomous versus **64% assisted** ([arXiv 2410.03225](https://arxiv.org/abs/2410.03225)), which supports Lateralis's human-approval design. **Incalmo/MHBench** reached critical assets in 37 of 40 multi-host networks through a high-level action abstraction, against 3 of 40 for the best prior LLM system ([Incalmo v4](https://arxiv.org/html/2501.16466v4)). Abstraction mattered more than model size, which is good news for a red-team agent driving Caldera abilities on free-tier models. The defensible story for Lateralis is therefore **relative improvement over baselines**, not absolute state of the art.

The main result for every agent should come from a custom **Lateralis-IncidentBench** built with ExCyTIn's recipe. Run 10–20 Caldera and Atomic adversary profiles across 3–4 lab topologies, with varied seeds, start hosts and benign noise. Ingest the telemetry through the same pipeline the GNN uses. Auto-generate tasks of four kinds: single-hop lookups, multi-hop alert→entity→alert questions, full JSON incident reconstructions, and rubric-judged reports. ExCyTIn built each incident as an alert–entity graph, used shortest paths as gold reasoning chains, and turned 7,542 candidates into 589 test questions ([arXiv 2507.14201](https://arxiv.org/html/2507.14201v1)). Two of its findings set rules for the split. Alert-only data *raised* reward to 0.459, so include raw-telemetry tasks. Fine-tuning on 253 successful trajectories overfit to held-out incidents, so hold out whole adversary profiles and at least one unseen topology. Lab-generated incidents also avoid contamination from public CTI text in pretraining data. The same runs give the GNN its multi-campaign forecasting ground truth, so agents and model report on identical incidents.

|---|---|---|---|---|
| Analyst/triage | ExCyTIn subset if downloadable; AttackSeqBench sample ([arXiv 2503.03170](https://arxiv.org/html/2503.03170v3)); CTI-ATE; `cyse4_threat_intelligence --limit 100` | Technique F1, host-set Jaccard, path-edge F1, Kendall τ over order, ExCyTIn-style decayed partial credit, tool-call precision and recall, query success rate (Pearson **0.86** with reward in ExCyTIn) | Sigma-only mapping; LLM without tools; with vs without reflection (k=3 lifted GPT-4o-mini from 0.192 to 0.452 in ExCyTIn); **with vs without the GNN forecast** | Premature-submit rate; injection ASR |

Rigour needs a few fixed rules. Use a judge from a different model family than the agent, score pairwise comparisons in both orders, use discrete rubric anchors, and report **Cohen's κ against 30–50 human-labelled items**. Judge biases (position, verbosity, self-preference) are documented, as is >80% GPT-4 agreement with humans ([MT-Bench, arXiv 2306.05685](https://arxiv.org/abs/2306.05685)). Run k = 3–5 repeats and report pass@k alongside pass^k, the probability that *all* k trials succeed, which τ-bench introduced to expose unreliable agents ([arXiv 2406.12045](https://arxiv.org/abs/2406.12045)). Use Wilson or bootstrap 95% CIs and McNemar's test for paired A/B comparisons. Log model version, prompt version, temperature, tokens, latency and rate-limit retries on every call. **Inspect AI** is the harness: it packages CyberSecEval 4, CyberMetric and Cybench, sandboxes in Docker, and accepts custom tasks. Add promptfoo for injection regression in CI.

The cheapest original experiment is a **pseudonymization A/B on a local model**: raw vs consistent structure-preserving pseudonyms vs naive `[IP]` masking, on at least 50 incidents. A local model keeps the raw arm on the machine. General NLP results suggest the gap depends on the task: redaction cost 1–5% on classification but more than 25% on comprehension QA ([arXiv 2411.05978](https://arxiv.org/html/2411.05978v1)). No study measures the effect on security investigation agents, so whatever Lateralis measures is new.

## Incumbents map static paths; no one publishes calibrated forecasts

Every major attack-path and exposure product found builds its graph from **configuration and posture data**: Microsoft Security Exposure Management generates paths "automatically" from device, identity and cloud data ([MS Learn](https://learn.microsoft.com/en-us/security-exposure-management/work-attack-paths-overview)). XM Cyber ranks choke points on an attack graph, and its own research claims only 2% of paths reach critical assets ([SecurityWeek](https://www.securityweek.com/most-attack-paths-are-dead-ends-but-2-lead-to-critical-assets-report/amp/)). Wiz (closed into Google for $32B in March 2026) ranks exploitable cloud paths ([TechCrunch](https://techcrunch.com/2026/03/11/google-completes-32b-acquisition-of-wiz/)). BloodHound maps identity graphs. Horizon3.ai and Pentera validate by exploiting rather than predicting. Lateral-movement detection vendors split into detection-led AI (Vectra, Darktrace) and prevention (Zero Networks, Illumio, Silverfort). The data for static paths is also getting harder to collect: Microsoft Defender for Identity disabled the remote SAM-R collection that fed its lateral-movement paths in May 2025 ([MC1073068](https://mc.merill.net/message/MC1073068)). The only commercial temporal-GNN example found is **Akamai Hunt**, whose 2023 blog describes GNN+RNN link prediction on network snapshots for anomaly flagging, **with no accuracy figures published** ([Akamai](https://www.akamai.com/blog/security/2023/oct/detect-and-remediate-attacks-with-akamai-hunt)).

The agentic SOC market is crowded and saturated with hype. Microsoft, Google, CrowdStrike, Palo Alto and SentinelOne all ship triage agents, with human approval for high-impact actions as the norm. CrowdStrike "does not take automated response actions by default" ([CrowdStrike](https://www.crowdstrike.com/en-us/platform/charlotte-ai/)), and Cortex AgentiX lets admins define when agents need approval ([Palo Alto Networks](https://www.paloaltonetworks.com/company/press/2025/palo-alto-networks-unveils-cortex-agentix-to-build--deploy-and-govern-the-agentic-workforce-of-the-future)). Every performance claim is vendor-reported. Gartner's June 2026 Hype Cycle puts AI SOC agents at the **Peak of Inflated Expectations with 1–5% penetration** ([Vectra summary](https://www.vectra.ai/topics/agentic-soc)). All the commercial products are SaaS, but self-hosting with local LLMs is **not** unique: **AiSOC** (MIT, about 7.1k stars) already offers self-hosted auto-triage with Ollama/vLLM and an investigation ledger ([AiSOC](https://github.com/beenuar/AiSOC)).

That leaves a sharp positioning: *"BloodHound shows the paths that exist. Lateralis forecasts the one an attacker is most likely to take next, from your live auth and network logs, with calibrated probabilities, and recommends the cheapest control that cuts the most probable paths to your crown jewels."* The claims below are ranked by how hard they are to dispute.

| Claim | Credible? | Why |
|---|---|---|
| Calibrated next-hop probabilities with published reliability diagrams on LANL/OpTC | **Yes, strongest** | No vendor and no academic lateral-movement paper publishes calibration |
| Forecast-weighted choke points × remediation cost | Yes | Extends the established choke-point vocabulary (XM Cyber, Microsoft) |
| Self-hosted, pseudonymized-before-egress agents | Yes, as a feature | The commercial agentic SOCs are all SaaS; AiSOC already covers the open-source side |
| Red-team lab validating the forecast | Yes | Fits Gartner's expected convergence of exposure assessment and validation ([XM Cyber recap](https://xmcyber.com/blog/initial-reactions-and-key-takeaways-from-the-2026-gartner-security-and-risk-summit/)) |
| "First GNN for lateral movement" / "first open-source AI SOC" | **No** | Euler, Jbeil and Akamai; AiSOC and Vigil |

For delivery, copy **BloodHound CE/Enterprise**: one codebase, a free `docker compose up` community edition bound to localhost, a documented REST API with HMAC-signed tokens (token ID + secret over method, URI, date and body), and paid enterprise features plus support ([BloodHound API](https://bloodhound.specterops.io/integrations/bloodhound-api/working-with-api)). The licence choice is a real fork in the road. **Apache-2.0** maximises adoption (BloodHound CE, Caldera, OpenCTI CE) but allows SaaS free-riding. **AGPL-3.0 core plus an `/ee` directory under a commercial key** is the recent open-core pattern (Tracecat, OpenCTI) ([OpenCTI EE docs](https://docs.opencti.io/latest/administration/enterprise/)). TheHive's move from AGPL to proprietary freemium with a 2-user community cap ([StrangeBee](https://docs.strangebee.com/thehive/installation/licenses/about-licenses/)) shows why the licence should be fixed up front. For an Indian market, sovereignty is a concrete selling point. CERT-In requires **6-hour incident reporting and 180-day log retention** ([Nishith Desai](https://nishithdesai.com/research-and-articles/hotline/technology-law-analysis/cert-in-releases-faqs-explaining-the-direction-on-cybersecurity-6139)). The DPDP Rules were notified on 14 November 2025, with penalties up to **₹250 crore** for inadequate safeguards ([PIB](https://static.pib.gov.in/WriteReadData/specificdocs/documents/2025/nov/doc20251117695301.pdf)). The cross-border negative list is still empty and expected around May 2027 ([Mondaq](https://www.mondaq.com/india/data-protection/1764976/from-localisation-debates-to-a-negative-list-making-cross-border-data-transfers-work-under-indias-dpdp-act)). Pseudonymizing identifiers before any foreign LLM call is therefore a defensible design, though this is an inference, not legal advice.

A sensible build order puts the evaluation first. Build the LANL streaming pipeline and the Larroche protocol, with EdgeBank and heuristic baselines, before touching the platform. Packaging and licensing come last.

## Conclusion

The most valuable thing Lateralis can contribute is not a better model but **a field-standard way to evaluate next-hop forecasting**: event-level metrics on Larroche's protocol, TGB-style ranking against EdgeBank, and calibration of the probabilities that Yen's algorithm actually consumes. That inverts the usual student-project risk. Modest absolute numbers become a strength, because the field's published 99% AUCs are now known to be artefacts, and a project that reports honest AP, MRR and ECE with confidence intervals stands out against vendors that publish nothing measurable. The Docker lab is the hinge of the whole design. One set of Caldera runs gives the GNN multi-campaign forecasting ground truth, gives every agent a contamination-free benchmark, and closes a purple-team loop in which the red-team agent tests the forecaster.

The platform layer is commodity, and that's fine. The agents, approval gates, redaction and Compose packaging all have proven open-source patterns (LangGraph interrupts, Presidio's instance-counter tokens, BloodHound's localhost-bound Compose and HMAC API). What makes them more than an AiSOC clone is grounding: every agent action should cite a forecast, a path probability or a choke point. The binding constraints are external and fragile: free-tier quotas that have already shrunk this year, and Windows telemetry a Linux lab can only approximate. Design for both to get worse. Keep a local-model fallback and treat LANL as the Windows anchor, so the core research result never depends on them.
